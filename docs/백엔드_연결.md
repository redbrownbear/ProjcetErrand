# 백엔드 연결 (Firebase)

마이 화면의 하드코딩된 숫자를 걷어내고, 프로필·부탁글·활동 기록을 Firestore로 옮긴 기록이다.

Firebase 프로젝트: **projecterrand** (Android + 웹 앱 등록 완료)

## 1. 데이터 구조

```
users/{uid}                     프로필
  email, nickname, region, verified, points, createdAt, updatedAt
  migratedFromDevice            이 기기 기록을 계정으로 옮겼는지 (중복 업로드 방지)

  bookmarks/{requestId}         관심 저장   { createdAt }
  trades/{requestId}            지원·거래   { status, updatedAt, title, price, mode }
  offers/{requestId}            가격 제안   { items: [{price, msg}], updatedAt }
  coupons/{couponId}            쿠폰       { brandK, name, points, exp, code, used, createdAt }
  ledger/{rewardKey}            적립 원장   { on, amount, label, claimedAt }

requests/{requestId}            공개 부탁글 (문서 id = TaskItem.id, 밀리초 타임스탬프)
  ownerUid, who, mode, cat, title, desc, region, place, deliveryPlace,
  country, cc, city, lat, lng, distM, mins, price, budget, payment,
  completion, hot, deadline, status('open'|'closed'), createdAt, updatedAt
```

내 자료를 전부 `users/{uid}` 아래에 둔 이유는 보안 규칙을 "본인만"으로 한 줄에 끝내기 위해서다.
포인트·쿠폰·지원 내역은 남이 볼 이유가 없다.

**적립 원장(`ledger`)이 서버에 있는 게 중요하다.** 예전에는 메모리에만 있어서 앱을 껐다 켜면
출석 보상을 다시 받을 수 있었다. 이제 기기를 바꿔도 하루에 한 번이다.

## 2. 마이 화면의 숫자는 어디서 오나

| 항목 | 출처 |
| --- | --- |
| 닉네임·이메일·활동 지역·본인인증 | `users/{uid}` |
| 보유 포인트 | `users/{uid}.points` |
| 도와준 횟수 | 내 `trades` 중 완료, 그리고 **내 글이 아닌** 것 |
| 부탁한 횟수 / 내가 올린 부탁 | `requests` 중 `ownerUid == 나` |
| 거래 완료 | 내 `trades` 중 완료 |
| 진행 중 | 내 `trades` 중 완료·취소가 아닌 것 |
| 이번 달 받은 사례비 / 누적 | 완료 거래의 사례비 합 (완료 시각 기준) |
| 관심 저장 / 지원한 부탁 / 쿠폰 | 각 하위 컬렉션 개수 |
| 응답률 · 후기 평점 | **'—'** — 후기 기능이 없으므로 숫자를 지어내지 않는다 |

계산은 서버 집계 필드가 아니라 앱이 기록을 세서 한다. 같은 숫자를 두 곳에 저장하면
반드시 어긋나고, 그 순간 어느 쪽이 맞는지 알 수 없게 된다.

## 3. 서버가 없어도 앱은 뜬다

`main()`이 `Firebase.initializeApp`을 try/catch로 감싸고 결과를 `Backend.ready`에 기록한다.

- `ready == true` → Firestore를 쓰고, 이 기기(`LocalStore`)에는 오프라인 사본을 남긴다
- `ready == false` → 전부 `LocalStore`로만 동작하고, 마이 화면 위에 **빨간 안내 줄**이 뜬다

서버 호출은 전부 `Backend.guard`/`Backend.push`를 지난다. 10초 안에 응답이 없거나
실패하면 조용히 로컬 값으로 되돌아가고 화면은 멈추지 않는다.

`AuthService`도 플러그인 객체를 필드로 붙잡지 않는다. Firebase가 없는 환경에서
`AuthService()`를 만드는 것만으로 예외가 나면 화면이 통째로 하얘지기 때문이다.

## 4. 첫 로그인 이관

로그인하면 이 기기에 있던 부탁·관심 저장·지원 내역·가격 제안을 계정으로 한 번 올리고,
`users/{uid}.migratedFromDevice = true`를 남긴다. 문서 id가 곧 부탁 id라 두 번 올려도
복제가 아니라 덮어쓰기지만, 쓸데없는 호출을 막는다.

예시(시드) 데이터는 **올리지 않는다.** 화면을 채우는 용도일 뿐이고, 올려 두면 다른
사용자 눈에 진짜 모집 글로 보인다.

## 5. Firebase 콘솔에서 해주셔야 하는 것

1. **Firestore Database 만들기**
   콘솔 > Firestore Database > 데이터베이스 만들기 > 위치 `asia-northeast3`(서울) 권장.
   모드는 프로덕션으로 두고 아래 규칙을 붙여넣으세요.

2. **보안 규칙 게시**
   `firebase/firestore.rules` 내용을 콘솔 > Firestore Database > 규칙에 붙여넣고 '게시'.
   규칙을 안 올리면 기본 잠금 상태라 읽기·쓰기가 전부 막힙니다.

3. **복합 색인 하나**
   홈 목록이 `status == 'open'`으로 거르고 `createdAt` 내림차순으로 정렬합니다.
   `firebase/firestore.indexes.json`에 정의해 뒀고, 콘솔에서 직접 만들어도 됩니다.
   (안 만들면 콘솔 로그에 색인 생성 링크가 찍히니 그걸 눌러도 됩니다)
   - 컬렉션 `requests` · `status` 오름차순 · `createdAt` 내림차순

4. **이메일/비밀번호 로그인 켜기**
   콘솔 > Authentication > Sign-in method > 이메일/비밀번호 사용 설정.

5. **Windows에서 로그인하려면** 콘솔 > Authentication > Settings > 승인된 도메인에
   `localhost`가 있어야 합니다.

## 7. 아직 안 한 것

- **요청자 쪽 수락·알림.** 지원하면 내 `trades`에만 기록되고 요청자에게 전달되지 않습니다.
  제대로 하려면 `requests/{id}/applications/{uid}` 같은 하위 컬렉션과 푸시 알림이 필요합니다.
- **후기·평점.** 컬렉션도 화면도 아직 없어서 마이 화면에 '—'로 둡니다.
- **정산.** 금액은 기록일 뿐 실제 이체가 아닙니다.
- **포인트 검증.** 지금은 앱이 포인트를 계산해 쓰기 때문에, 마음먹으면 조작할 수 있습니다.
  실서비스로 가려면 적립·차감을 Cloud Functions에서 처리해야 합니다. → [10. 포인트](#10-포인트)

## 8. 겸사페이 (구조만)

포인트가 두 종류로 갈라졌다. 성격이 달라서 **끝까지 섞지 않는다.**

| | 겸사페이 | 포인트 |
| --- | --- | --- |
| 단위 | 원 (실제 돈) | P (리워드) |
| 어디서 | 완료한 부탁의 사례비, 충전 | 부업·미션·출석 |
| 어디에 쓰나 | 출금, 부탁 비용 결제 | 상품 교환 |
| 저장 | `users/{uid}/payEntries/{id}` (원장) | `users/{uid}.points` |

두 값을 한 숫자로 합쳐 보여주면 "출금하면 얼마 들어오나"를 알 수 없게 된다.
홈 지갑 카드에서도 따로 두고, 합계는 **목표 달성률에만** 쓴다.

### 잔액을 저장하지 않는 이유

`payEntries`는 append-only 원장이고, 잔액은 `PayEntry.balanceOf()`로 매번 더해서 만든다.
돈이 걸린 값에서 잔액과 내역을 따로 저장하면, 둘이 어긋났을 때 어느 쪽이 맞는지 알 수 없다.
게다가 지금은 **앱이 원장을 쓰기 때문에** 잔액까지 앱이 쓰면 마음먹은 사람이 숫자를 고칠 수 있다.
기록만 남기면 최소한 앞뒤가 맞는지는 눈으로 확인된다.

### 지금 되는 것 / 안 되는 것

- ✅ 거래를 완료하면 사례비가 원장에 `earn`으로 한 줄 쌓인다 (내가 올린 부탁은 제외)
- ✅ 잔액·내역 화면, 로그인 시 서버 동기화, 첫 로그인 이관
- 🔒 **충전·출금은 디버그 빌드에서만** 동작한다 (`PayConfig.debugTopUp`)

### 개발용 충전·출금 (`PayConfig`)

법령 검토 전까지는 흐름만 만져볼 수 있게 디버그 빌드에서만 통로를 열어 둔다.
실제 돈은 1원도 움직이지 않고, 원장에 `개발용 충전` / `개발용 출금`으로 남는다.
화면에도 파란 '개발용 모드' 안내가 뜬다.

`PayConfig.debugTopUp`은 `kDebugMode`를 그대로 쓴다. 컴파일 타임 상수라
**릴리스 빌드에서는 이 값을 보는 분기 전체가 트리 셰이킹으로 사라진다** —
실수로 켠 채 배포되는 일이 없다. 화면과 `HomeShell` 양쪽에서 한 번씩 막는다.

### 실제로 돈을 움직이려면

1. **결제사(PG) 계약과 충전 콜백** — 카드·계좌에서 실제로 받는 경로
2. **본인 명의 계좌 인증** — 출금 대상이 본인인지 확인
3. **Cloud Functions 트랜잭션** — 원장 쓰기를 서버로 옮겨야 앱을 못 믿어도 숫자를 믿는다
4. **전자금융거래법 검토** — 선불전자지급수단에 해당하면 등록 의무가 생긴다

4번은 개발 이전의 문제다. 잔액을 보관했다가 나중에 쓰게 하는 순간 규제 대상이 될 수 있으니,
충전 기능을 붙이기 전에 확인이 필요하다.

## 9. 신뢰 레벨

`users` 문서에 저장하지 않고 거래 기록에서 매번 센다 (`TrustLevel.from`).
거래 기록이 원본이고 레벨은 거기서 나온 값이라, 두 곳에 두면 언젠가 어긋난다.

| 행동 | 점수 |
| --- | --- |
| 거래를 끝까지 마침 | +10 |
| 그중 내가 도와준 쪽 | +5 더 |
| 본인인증 | +20 |
| 시작한 거래를 취소 | −5 |

Lv.1 새싹 이웃(0) → Lv.2 동네 이웃(30) → Lv.3 믿음직한 이웃(80) →
Lv.4 든든한 이웃(160) → Lv.5 동네 반장(300)

**후기 점수는 넣지 않았다.** 후기 기능이 없어서 넣을 값이 없고, 억지로 섞으면
나중에 진짜 후기가 들어왔을 때 레벨이 이유 없이 출렁인다.

다른 사람의 레벨을 보여줄 때가 되면 서버 집계로 옮겨야 한다. 그건 후기 기능과 같이 가는 작업이다.

## 10. 포인트

리워드 포인트(P)를 어디서 받고, 어디에 쓰고, 어디에 저장하는지 한곳에 정리한다.
겸사페이(원)와는 별개다 → [8. 겸사페이](#8-겸사페이-구조만).

### 지금 구조

| 단계 | 하는 곳 | 코드 |
| --- | --- | --- |
| 적립 | 앱 | `HomeShell.earn(amt, label, key:, daily:)` — 로그인 필수 |
| 중복 확인 | 앱 | `RewardLedger.claimValue(key)` — 같은 키는 하루(또는 계정당) 한 번 |
| 잔액 변경 | 앱 | `points += amt` / 교환 시 `points -= 상품가` |
| 서버 저장 | 앱 → Firestore | `users/{uid}.points`(잔액), `users/{uid}/ledger/{key}`(적립 기록) |
| 교환 | 앱 | `HomeShell.redeem` → `users/{uid}/coupons/{id}` + 잔액 차감 |

**적립 키(`key`)** 가 중복 지급을 막는 장치다. 같은 보상은 어느 화면에서 눌러도 같은 키를 쓴다.

| 적립처 | 키 | 한도 |
| --- | --- | --- |
| 출석 | `benefit:attend:YYYY-MM-DD` (`Attendance.keyFor`) | 하루 1번 (연속·월 보너스 포함 금액) |
| 데일리 미션 | `daily:{id}` 또는 회차형 `daily:{id}#{n}` (`DailyMission.ledgerKey`) | 미션별 `cap` (광고 시청 `daily:ad#0~2`, 하루 3번) |
| 제휴 미션 | `mission:{id}` | 계정당 1번 |
| 공동구매·기타 혜택 | 화면별 고정 키 | 화면에 적힌 대로 |

하루의 기준은 **한국 시간(UTC+9)** 이다 (`RewardLedger.todayKey`). 기기 시간대와 무관하다.

단가는 전부 `lib/features/benefits/data/point_rules.dart`에 모여 있다. 재원에서 역산한 값이고,
**낮게 시작해 올리는 방향으로만** 바꾼다 ([제휴_API_연동.md](제휴_API_연동.md) '포인트 단가 재측정').

### 지금 구조의 빈틈

1. **앱이 잔액을 직접 쓴다.** `users/{uid}.points`를 앱이 덮어쓰고, 보안 규칙은 "본인이면 쓰기 허용"이다.
   마음먹으면 잔액을 아무 숫자로 바꿀 수 있다.
2. **차감 기록이 없다.** 교환하면 잔액만 줄고 `ledger`에는 아무것도 안 남는다. 적립 원장만으로는
   지금 잔액이 맞는지 다시 계산할 수 없다.
3. **잔액과 원장이 따로 저장된다.** 적립 때 `saveLedgerEntry`와 `savePoints`를 각각 부른다.
   하나만 성공하면 둘이 어긋난다 (트랜잭션이 아니다).
4. **광고 시청 검증을 앱이 한다.** "끝까지 봤다"를 앱이 믿고 적립한다. 광고 SDK가 서버 검증 콜백을
   주면 그걸로 바꿔야 한다.
5. **소멸·유효기간이 없다.** 약관에 유효기간(관행 180일)을 정하지 않으면 나중에 소멸 처리를 못 한다.

### 바꿀 구조 (Cloud Functions)

겸사페이와 같은 원칙이다 — **원장이 원본, 잔액은 원장에서 나온 값, 쓰기는 서버만.**

```
users/{uid}
  points                     잔액 사본 (서버만 씀, 화면 표시용)
  pointLedger/{entryId}      포인트 원장 (append-only, 서버만 씀)
    type     earn | spend | expire | revoke
    amount   +적립 / −차감
    key      적립 키 (earn일 때 — 문서 id로 써서 중복 방지)
    label    '출석 적립', '광고 보고 적립', '메가커피 아메리카노 교환' …
    ref      관련 문서 (쿠폰 id, 미션 id, 광고 거래 id)
    at       서버 시각
    expireAt 적립분의 소멸 예정일
```

| 함수 | 하는 일 |
| --- | --- |
| `earnPoints(key, kind)` | 키와 오늘 날짜로 중복을 확인하고, **금액은 서버가 `point_rules`와 같은 표로 정한다** (앱이 보낸 금액을 믿지 않음). 원장 한 줄 + 잔액을 한 트랜잭션으로 |
| `redeem(productId)` | 상품가를 서버 표에서 읽고, 잔액이 모자라면 거절. 차감 원장 + 쿠폰 발급 + 잔액을 한 트랜잭션으로 |
| `adRewardCallback` | 광고 회사의 시청 완료 서버 콜백을 받아 서명 확인 후 `earnPoints`. 같은 광고 거래 id는 한 번만 |
| `expirePoints` (매일 예약 실행) | `expireAt`이 지난 적립분을 `expire`로 차감 |

보안 규칙은 이렇게 좁힌다.

- `users/{uid}`의 `points` 필드와 `pointLedger`, `coupons`는 **앱이 쓰지 못하게** 막는다 (읽기만 본인).
- 앱은 함수만 부른다. 지금의 `ledger/{rewardKey}`는 옮긴 뒤 읽기 전용으로 두었다가 지운다.

### 옮기는 순서

1. `pointLedger`와 함수 네 개를 만들고, 앱의 `earn`·`redeem`이 함수를 부르게 바꾼다.
2. 기존 사용자는 `points` 잔액을 `earn`(label: '이전 잔액') 한 줄로 원장에 넣어 시작점을 맞춘다.
3. 보안 규칙에서 앱의 `points`·`ledger`·`coupons` 쓰기를 막는다.
4. 약관에 유효기간·소멸·단가 변경 근거를 넣고 `expirePoints`를 켠다.

광고 보고 포인트 받기는 이 작업이 끝난 뒤에 실제 광고와 연결하는 게 맞다. 서버 검증 없이
광고 적립을 열면 1번·4번 빈틈으로 포인트가 새어 나간다.
