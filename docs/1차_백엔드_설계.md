## 2. 작업 갈래

갈래 번호는 W(Workstream)로 붙이고, 허브 개발 To-do 코드와 연결한다. 순서는 의존 관계 순이다.

### W1 서버 기반 구성 — A01

- 목표: 서버 코드를 저장소에서 관리하고 배포·테스트할 수 있게 한다.
- 할 일
  - `firebase.json` · `.firebaserc` · `functions/`(TypeScript, Node 20, 리전 `asia-northeast3`) 추가
  - 규칙·색인을 CLI로 배포(`firebase deploy --only firestore`), 콘솔 붙여넣기 중단
  - Firebase Emulator Suite로 규칙·함수 테스트(`@firebase/rules-unit-testing`, functions 테스트)
  - App Check: Android Play Integrity, 디버그 토큰. 처음엔 **모니터링 모드** → 1차 출시 직전 강제
  - 환경 분리: 개발용 Firebase 프로젝트를 따로 둘지(결정 3)
  - Blaze 요금제 전환(Functions 필수) + **예산 알림** 설정
- 검증 기준: 에뮬레이터에서 규칙 테스트 통과, `firebase deploy` 한 번으로 규칙·색인·함수 배포, 콘솔에 예산 알림 등록 확인

### W2 DB 구성(데이터 모델 v2) — A02 · A03

원칙: **공개 정보와 거래 당사자 정보를 문서 단위로 나눈다.** 상태를 바꾸는 쓰기는 서버만 한다.
거래 상태와 금전 상태를 섞지 않는다(결제는 나중에 `payments/`로 따로).

```
users/{uid}                     본인만 읽기. 앱은 nickname·region 등 프로필 필드만 쓰기
                                points · verified · role · stats 는 서버만
  fcmTokens/{token}             본인 쓰기
  notifications/{id}            본인 읽기, 서버 쓰기
  blocks/{targetUid}            본인 읽기·쓰기
  bookmarks/{requestId}         (유지)
  routes/{routeId}              정기 동선 — W6
  pointLedger/{entryId}         서버만 쓰기 — W7

publicProfiles/{uid}            누구나 읽기: nickname · area · trustLevel · 완료 수 (서버만 쓰기)

requests/{requestId}            누구나 읽기(공개 정보만)
  ownerUid, mode, cat, title, desc, price, budget, deadline,
  area(동/구 이름), cell(geohash 5자리, 약 5km 격자),
  status: open | matched | done | cancelled | expired,
  applicantCount, createdAt, updatedAt
  private/detail                글쓴이 + 수락된 수행자만: 정확 좌표, place, deliveryPlace, 연락 메모
  applications/{helperUid}      글쓴이와 지원자 본인만 읽기, 서버만 쓰기
    offerPrice, msg, status: pending | accepted | rejected | withdrawn, createdAt

trades/{tradeId}                요청자·수행자만 읽기, 서버만 쓰기
  requestId, requesterUid, helperUid, price(합의 금액 사본),
  status: matched | working | confirmation | completed | cancelled,
  history: [{status, by, at}], cancelReason?
  messages/{id}                 채팅(결정 5 이후)

reports/{id}                    작성자 create만, 운영자 읽기
```

- 부탁 문서 id: 지금처럼 앱의 밀리초 int를 유지하면 `TaskItem.id:int`를 건드리지 않아도 된다(최소 변경).
  다만 생성은 규칙에서 필드 검증 + `status=='open'` 강제 + `create` 전용으로 막는다(결정 2).
- 기존 `users/{uid}/trades`·`offers`: 프로토타입 기록이라 이관하지 않고 읽기 전용으로 두었다가 삭제(결정 4).
- 검증 기준: 규칙 테스트로 아래를 모두 거부 — 남의 부탁 수정, 부탁 `status` 직접 변경, `applications`·`trades` 직접 쓰기, 비당사자의 `private/detail`·`trades` 읽기, `points` 직접 수정

### W3 거래 흐름 서버화 — A04 · A07 (A03 상태 머신)

Callable Functions(모두 로그인·App Check 필요, 역할·현재 상태를 트랜잭션 안에서 검사):

| 함수 | 누가 | 하는 일 |
| --- | --- | --- |
| `applyToRequest(requestId, offerPrice?, msg?)` | 지원자 | 본인 글·마감·중복·차단 관계 확인 → `applications` 생성, `applicantCount+1` |
| `withdrawApplication(requestId)` | 지원자 | pending일 때만 |
| `acceptApplication(requestId, helperUid)` | 글쓴이 | 부탁 open 확인 → `trades` 생성, 부탁 `matched`, 나머지 지원 `rejected` |
| `rejectApplication(requestId, helperUid)` | 글쓴이 | pending → rejected |
| `advanceTrade(tradeId, action)` | 역할별 | start·finish = 수행자 / confirm·revise = 요청자 / cancel = 시작 전 양쪽 |
| `cancelRequest(requestId)` | 글쓴이 | 매칭 전만 |
| `expireRequests` (예약 실행, 1시간) | 서버 | 마감 지난 open → expired |

상태 전이 표는 지금 `Trade._transitions`를 그대로 서버로 옮기고, **누가 누를 수 있는지**만 더한다.
앱 쪽 변경: `AppSession.apply`·`updateTrade`가 함수를 부르고, 결과는 Firestore 구독으로 받는다.
'요청자 수락 체험' 버튼은 제거하고, 요청자 화면에 '받은 지원' 목록을 만든다.
거래 완료 때 앱이 `payEntries`·응모권을 쓰던 코드는 끈다(결제 미정, 결정 6).

- 검증 기준: 에뮬레이터 통합 테스트 — 두 계정으로 지원 → 수락 → 시작 → 완료 → 확인, 역할이 틀린 호출과 순서를 건너뛴 호출은 모두 거부, 같은 호출을 두 번 보내도 상태가 한 번만 바뀜

### W4 알림 — A05

- 앱: `firebase_messaging` 추가, 토큰을 `users/{uid}/fcmTokens`에 저장, 알림 권한 요청(Android 13+)
- 서버: `trades`·`applications` 변경 트리거 → `notifications` 기록 + FCM 발송
- 1차 알림 종류: 새 지원(요청자), 수락·거절(지원자), 단계 변경(상대), 완료 확인 요청, 신고 처리 결과
- 제한: 거래 알림은 즉시. 추천 알림(W9)은 하루 상한·야간(21~08시) 금지. 마케팅성 알림은 1차에 없음
- 검증 기준: 실기기 두 대로 각 알림 수신, 토큰 만료 시 정리, 같은 이벤트 중복 발송 없음(이벤트 id로 멱등)

### W5 신고·차단·운영 — A22

- 신고: `reports` 생성(대상 사용자·부탁·거래, 사유), 운영자 처리 상태
- 차단: `users/{uid}/blocks`. 서버 함수가 지원·수락 때 양방향 차단을 확인, 목록 조회는 앱에서 거름
- 운영자: Auth custom claim `role=admin`. 1차 운영 도구는 **스크립트 + Firebase 콘솔**(부탁 숨김, 사용자 정지 `users/{uid}.suspended`, 신고 처리). 어드민 웹은 후속(결정 7)
- 검증 기준: 차단한 사용자는 내 부탁에 지원 불가, 정지 사용자는 모든 함수 거부, 신고는 운영자만 읽기

#### 운영 방법 (1차)

1. 운영자 지정: Firebase 콘솔 › 프로젝트 설정 › 서비스 계정 › 새 비공개 키 생성(저장소 밖에 보관) →
   `cd functions && GOOGLE_APPLICATION_CREDENTIALS=<키 경로> node scripts/set-admin.js <이메일>` → 그 계정으로 다시 로그인
2. 신고 확인 · 처리: 운영자 계정으로 앱 › 마이 › **운영 › 신고 처리**(A36, 운영자 계정에만 보임) — 처리 전/처리됨 목록,
   신고 한 건에서 문제 없음 · 경고 · 이용 정지, 정지 풀기, 신고된 글 내리기 · 되돌리기.
   서버 함수는 `adminResolveReport({reportId, resolution: dismissed|warned|suspended, memo})`(경고 → 대상에게 `report.warned`,
   처리 → 신고자에게 `report.resolved` 알림), `adminSetSuspended({uid, suspended, reason})`,
   `adminSetRequestHidden({requestId, hidden, reason})`(운영자가 내린 글만 `hiddenBy: 'admin'`이라 되돌릴 수 있다). 모든 처리는 `adminLog`에 남는다
   신고가 들어오면 서버(`onReportCreate`, A34)가 유형(`category`) · 긴급도(`priority`: urgent 위험한 말 · high 사기/금지 품목/욕설이나 최근 7일 3명 이상 신고)
   · 근거(`signals`)를 붙이고 신고자에게 유형별 1차 안내(`report.received`)를 보낸다. 처리 전 목록은 급한 것부터. 경고 · 정지는 자동으로 하지 않는다
3. 콘솔로 볼 때: Firestore 콘솔 › `reports` (상태 없는 것이 미처리)
4. 급할 때: 콘솔에서 `users/{uid}.suspended = true`로 직접 정지해도 거래 함수가 막는다(기록은 남지 않음)
5. 공지 · 업데이트(A33): `node scripts/post-notice.js <notice|update|event> "<제목>" <본문.txt> [--pin] [--at 2026-11-01T09:00]`(키는 1과 같다),
   내리기는 `--hide <id>`. 콘솔에서 `notices`에 직접 넣어도 된다(title · body · kind · pinned · hidden · publishedAt). 앱 › 마이 › 공지 · 업데이트

### W6 동선 구조화 — A02 · A08 · A09 · A11

목표: 추천에 쓸 최소 동선 데이터. **실시간 위치를 수집·저장하지 않는다.**

```
users/{uid}/routes/{routeId}      정기 동선 (F-001)
  from: {label, area, cell6}      사용자가 고른 역·동. cell6 = geohash 6자리(약 1.2km)
  to:   {label, area, cell6}
  days: [1..7], window: {start:"07:30", end:"08:30"}, mode: walk|transit|car|bike
  cells: [geohash 6자리…]         출발→도착 선분을 따라 서버가 계산한 격자 (W7 매칭용)
  active, createdAt, updatedAt
users/{uid}/trips/{tripId}        1회성 '가는 김에'(F-004) — 공개 글은 tripPosts/{id}에 area만
users/{uid}/departures/{id}       출국 일정(F-005) — 국가·도시·날짜만
```

- 좌표는 역·동 대표 좌표만 쓰고 geohash 6자리로 줄여 저장한다(정밀도는 D-12 결과에 따라 조정).
- `cells` 계산은 서버(`onRouteWrite`)가 한다. 앱이 보낸 격자를 믿지 않는다.
- 지금 기기에만 있는 '가는 김에' 글(`NeighborStore`)은 `tripPosts`로 옮긴다.
- 검증 기준: 동선 등록 2~3탭, 저장 문서에 정밀 좌표가 없음, 동선 삭제 시 `cells`까지 지워짐

### W7 추천 알고리즘 v0 — A13

전략 문서 §6대로 **단순한 조건 기반**으로 시작한다.

1. 부탁이 생성될 때(`onRequestCreate`) 한 번만 계산한다. 주기적 전체 스캔은 하지 않는다.
2. 후보 동선 = `routes`에서 `cells array-contains 부탁.cell6` + `active` + 요일 일치.
3. 시간 조건 = 동선 시간대가 부탁 마감 전에 있음.
4. 추가 소요 추정 = 픽업 지점과 동선 선분의 최단 거리 × 2 ÷ 이동수단 평균 속도. N분 이하만(기본값 N-02).
5. 알림 = 후보 중 사용자당 하루 상한, 야간 금지, 차단·본인 제외. 남는 후보는 앱의 '내 동선에 맞는 부탁' 목록에서 조회.
6. 외부 경로 API(네이버 길찾기)는 v0에서 쓰지 않는다(비용).

- 사용 데이터가 쌓이면 v1에서 실제 경로 기반 우회 시간, 수락률 반영 순위로 고도화.
- 검증 기준: 테스트 동선·부탁 세트에서 기대한 후보만 나옴, 부탁 1건당 Firestore 읽기 수 상한 확인, 상한 초과 알림 없음

### W8 포인트·보상 서버화 — B09 (1차 이후, 결정 6)

- `claimReward(kind, key)`: 출석·미션 보상 금액을 서버 표로 결정, `pointLedger` 원장 + `points` 사본을 한 트랜잭션으로, 키로 중복 방지
- `redeem(productId)`: 1차에 포인트샵이 없으면 만들지 않음
- 규칙에서 `points`·`ledger`·`coupons` 앱 쓰기 차단
- 검증 기준: 같은 보상 동시 호출 10회 → 1회만 적립, 앱에서 `points` 수정 시도 거부

### W9 비용 관리 — 전략 문서 §5

- 예산 알림(월 한도, 50·90·100%)
- 목록 구독 축소: 열린 부탁 200건 실시간 → 지역 셀 + 페이지 단위 조회, 실시간은 내 거래·내 지원만
- Functions: 최소 인스턴스 0, 리전 하나, 트리거 무한 루프 방지
- 네이버 지도·외부 API 호출량 대시보드
- 스타트업 크레딧 신청 여부 확인(전제로 삼지 않음)
- 검증 기준: 대표 시나리오(앱 열기→목록→상세→지원)의 읽기 수를 측정해 기록
