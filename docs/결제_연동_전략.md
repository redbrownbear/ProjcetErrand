# 결제 연동 전략 (자본금 0원 출발)

겸사페이를 실제로 열기까지의 순서와, 각 단계에서 붙일 SDK·API를 정한 문서다.
법령 검토 전까지 충전·출금은 디버그 빌드에서만 동작한다 (`PayConfig`).

## 원칙 셋

**1. 앱이 하는 말을 믿지 않는다.**
"결제 성공했어요"를 앱이 알려주면, 서버가 결제사에 **다시 물어서** 확인한 뒤에만 원장에 쓴다.
지금 `PayRepository`는 앱이 직접 Firestore에 쓰는데, 돈이 오가는 순간 이건 그대로 두면 안 된다.

**2. 결제사를 갈아끼울 수 있게 둔다.**
첫 PG 심사는 떨어질 수 있다. 수수료 협상도 거래액이 붙은 뒤에야 가능하다.
그래서 처음부터 애그리게이터를 써서, 하위 PG를 바꿔도 **앱 코드가 안 바뀌게** 한다.

**3. 받는 것과 주는 것을 따로 본다.**
마켓플레이스는 돈이 양방향으로 흐른다. 받기(결제)는 쉽고, 주기(지급)가 관문이다.
주기를 직접 하려면 PG 등록이 필요해서, 지급대행을 쓴다.

## 단계

| 단계 | 하는 일 | 전제 | 기간(대략) |
| --- | --- | --- | --- |
| 0 | 디버그 전용 지갑 | — | **완료** |
| 1 | 사업자등록 | 홈택스 온라인, 비용 0원 | 1일 |
| 2 | 결제(받기) 연동 | 1단계 + PG 가맹 심사 | 2~3주 |
| 3 | 본인인증 | 2단계와 같은 SDK | 3일 |
| 4 | 지급(주기) 연동 | 지급대행 계약 | 3~4주 |
| 5 | 충전형 잔액 | 법무 검토 + 한도 감시 | 검토 결과에 따라 |

**2단계 전에는 실제 돈이 1원도 안 움직인다.** 그때까지는 지금 구조 그대로 개발해도 된다.

### 1단계 — 사업자등록

PG 가맹 심사에 사업자등록증이 필요하다. 이게 없으면 그다음이 전부 막힌다.

- **개인사업자**: 홈택스에서 온라인 등록, 비용 0원, 당일 처리
- **법인**: 설립 비용이 들지만 PG 심사에서 유리하고, 나중에 투자받을 때 어차피 필요하다

0원으로 시작한다면 개인사업자로 열고, 거래액이 붙으면 법인 전환이 현실적인 순서다.
업종은 "통신판매중개업"에 가깝다 — PG 심사에서 반드시 묻는다. 미리 정리해 두면 빠르다.

### 2단계 — 결제 (받기)

**포트원(PortOne)을 쓴다.**

| 항목 | 값 |
| --- | --- |
| 패키지 | `portone_flutter` (pub.dev) |
| 발행자 | portone.io — **공식 verified publisher** |
| 버전 | 1.0.4 (2026-07) |
| 플랫폼 | Android · iOS |
| 지원 | 결제(V1·V2) + **본인인증** |
| 라이선스 | MIT |

주의: `portone_flutter_v2`는 커뮤니티 패키지이고 **단계적 중단** 상태다. 공식 `portone_flutter`를 쓴다.

포트원을 고른 이유는 셋이다.

- **애그리게이터**라 하위 PG(토스페이먼츠·나이스페이·KG이니시스…)를 콘솔에서 바꿀 수 있다. 원칙 2번.
- **본인인증이 같은 SDK에 있다.** 따로 연동할 게 없다 (3단계가 거의 공짜가 된다).
- 가입비·정기료가 없다. 하위 PG 수수료만 낸다.

직계약(토스페이먼츠 `tosspayments_widget_sdk_flutter`)이 나쁜 선택은 아니다. 문서가 제일 좋고
지급대행까지 한 곳에서 된다. 다만 PG를 갈아끼울 수 없어서, 거래액이 붙어 협상력이 생긴 뒤에
옮기는 편이 낫다.

### 3단계 — 본인인증

포트원 본인인증(통신사 PASS)을 쓴다. `portone_flutter`에 포함돼 있다.

성공하면 `users/{uid}.verified = true`로 올린다. 이미 만들어 둔 신뢰 레벨이 **+20점** 오른다
(`TrustLevel.verifiedBonus`). 인증할 이유를 사용자에게 만들어 주는 게 목적이다.

건당 과금(수십~수백 원)이라, **출금할 때만** 요구하는 게 합리적이다. 가입할 때 막으면 이탈만 는다.

### 4단계 — 지급 (주기)

2024년 9월 규정 개정으로, **플랫폼이 직접 도우미에게 정산하려면 PG 등록이 필요하다.**
자본금 요건이 있어서 초기에는 불가능하다. 그래서 지급대행을 쓴다.

후보: 토스페이먼츠 지급대행 · 세틀뱅크 · 페이업

계좌 인증(1원 인증)과 도우미 KYC가 보통 여기 포함된다. 따로 구하지 않아도 된다.

### 5단계 — 충전형 잔액

법무 검토 전에는 열지 않는다. 자세한 내용은 [백엔드_연결.md](백엔드_연결.md) §8.

## 서버 — Cloud Functions

돈이 오가는 순간 원장 쓰기를 전부 서버로 옮긴다. Firebase를 이미 쓰므로 Cloud Functions가 자연스럽다.

```
functions/
  payments/
    createPayment      결제 요청 생성 (주문번호 발급, 금액을 서버가 정함)
    webhook            포트원 웹훅 수신 → 결제사에 재조회 → 원장 기록
    cancelPayment      취소·환불
  payouts/
    requestWithdraw    출금 요청 (잔액 확인 → 지급대행 호출)
  ledger/
    onTradeCompleted   거래 완료 트리거 → 사례비 정산 기록
```

**금액을 앱이 정하게 두면 안 된다.** `createPayment`는 부탁 id만 받고, 금액은 서버가
`requests/{id}.price`에서 읽는다. 앱이 보낸 금액을 그대로 쓰면 1원 결제가 가능해진다.

**웹훅은 멱등이어야 한다.** 결제사는 같은 웹훅을 여러 번 보낸다. 주문번호를 문서 id로 써서
두 번 들어와도 한 번만 기록되게 한다. 지금 `payEntries`가 이미 id를 문서 id로 쓰는 구조라 그대로 간다.

같이 붙일 것:

- **Firebase App Check** — 이 Functions를 우리 앱만 부르게 막는다. 무료다.
- **Firestore 규칙 변경** — `payEntries` 쓰기를 클라이언트에서 막고 서버만 쓰게 한다

```
match /users/{uid}/payEntries/{id} {
  allow read: if isMe(uid);
  allow write: if false;   // Cloud Functions(Admin SDK)만 쓴다
}
```

| 용도 | 쓸 것 | 언제 |
| --- | --- | --- |
| 결제 | `portone_flutter` (공식, MIT) | 2단계 |
| 본인인증 | 같은 패키지의 certification | 3단계 |
| 서버 | Firebase Cloud Functions (Node.js) | 2단계 |
| 앱 검증 | Firebase App Check | 2단계 |
| 지급 | 토스페이먼츠 지급대행 / 세틀뱅크 (REST) | 4단계 |
| 계좌 인증 | 지급대행에 포함 | 4단계 |

**안 쓰는 것**: 오픈뱅킹(금융결제원) 직접 연동. 기관 자격이 필요하고, 지급대행을 쓰면 필요 없다.

## 수수료 — 구조부터 보기 (2026-09 확인)

**수단마다 과금 방식이 다르다.** 이걸 섞어서 생각하면 계산이 통째로 틀린다.

| 수단 | 구조 | 요율 / 단가 | 출처 |
| --- | --- | --- | --- |
| 신용카드 | **정률** | 일반 3.4% · 영세(연매출 3억↓) 1.6~1.9% | 토스페이먼츠 이용요금 |
| 간편결제 | **정률** | 3.4% (일부 추가 수수료) | 토스페이먼츠 이용요금 |
| 계좌이체 | **정률 + 최저액** | 2.0%, **최저 건당 200원** | 토스페이먼츠 이용요금 |
| 가상계좌 | **건당 정액** | 300~400원 | 토스페이먼츠 400원 / 코드엠샵 300원 |
| 휴대폰 | 정률 | 3.5~8% (상품 유형별) | 토스페이먼츠 이용요금 |

부가세 10% 별도. 일반과세자는 매입세액공제로 돌려받으므로 실질 원가는 아니다.

### 정률이면 나눠 충전해도 총액이 같다

30,000원을 한 번에 충전하든 10,000원씩 세 번 하든, **카드·간편결제는 총 수수료가 동일하다.**
"충전을 몰아서 하게 유도하면 이득"은 **가상계좌(정액)를 쓸 때만** 성립한다.
계좌이체는 최저 200원 때문에 **11,000원 미만 구간에서만** 부분적으로 성립한다.

### 금액대별로 싼 수단이 다르다

| 충전 금액 | 카드 3.4% | 계좌이체 2%(최저 200) | 가상계좌 400원 | 최저 |
| --- | --- | --- | --- | --- |
| 5,000 | 170 | 200 | 400 | 카드 |
| 10,000 | 340 | 200 | 400 | 계좌이체 |
| 20,000 | 680 | 400 | 400 | 계좌이체 ≈ 가상계좌 |
| 50,000 | 1,700 | 1,000 | 400 | **가상계좌** |

손익분기: 카드↔가상계좌 **약 11,800원**, 계좌이체↔가상계좌 **20,000원**.
→ **2만원 미만은 계좌이체, 2만원 이상은 가상계좌**를 기본값으로 올린다.
가상계좌는 은행 앱을 열어야 해서 UX 비용이 있으니, 기본값만 바꾸고 선택지는 나란히 둔다.

### 우대요율에 두 가지 함정이 있다

1. **신규 사업자는 첫 세금신고 전까지 우대를 못 받는다.** 출시 시점에는 일반 요율(3.2~3.5%)이다.
   첫 신고 후 차액을 소급 환급받는다(2026년 상반기 기준 15.9만 곳·약 615억 원).
2. **매출이 커지면 요율이 올라간다.** 등급은 1월·7월 반기마다 재산정된다.
   보통 사업은 규모가 커질수록 단가가 내려가는데, 카드 수수료는 반대다.

> **가맹 계약 전에 반드시 확인할 것**: 충전금 50,000원이 결제되면 카드 매출로는 50,000원이
> 잡히지만 우리 실매출은 중개수수료 5,100원뿐이다. 우대요율 등급이 **국세청 신고 매출** 기준인지
> **결제액** 기준인지에 따라 등급이 통째로 달라진다. PG에 서면으로 확인받아야 한다.

### 지급대행 (출금)

토스페이먼츠는 **"월 고정 이용료 + 지급 건당 이용료"**라고만 공시하고 금액은 비공개다(1544-7772 문의).
건당 단가는 견적을 받아야 확정된다. 참고로 은행 인터넷뱅킹 타행이체가 건당 500원 수준이므로
그 이하 대역으로 보는 게 합리적이지만, **숫자를 확정하기 전에는 손익 계산에 쓰지 않는다.**

지급은 **08:00~15:00 사이에 처리**되고, 바로지급과 예약지급(D+1~최대 1년)이 있다.

### 초기 비용

| 항목 | 초기 |
| --- | --- |
| 사업자등록(개인) | 0원 |
| 포트원 가입비·정기료 | 0원 |
| PG 가입비 | 평균 22만 원 (포트원 경유 시 면제 제휴 있음) |
| 토스페이먼츠 연 관리비 | 11만 원 |
| 하위 PG 수수료 | 첫해 3.2~3.5% → 이후 1.6~1.9% (거래 발생분만) |
| 본인인증 | 건당 수십~수백 원 |
| Cloud Functions | Blaze 전환 필요. 무료 할당량 안에서는 사실상 0원 |
| 지급대행 | 월 고정료 + 건당 요금 (견적 필요) |

**고정비가 거의 없다.** 거래가 없으면 나가는 돈도 거의 없는 구조다.

## 지금 코드에서 바꿔야 할 것

2단계에 들어갈 때 손댈 곳은 세 군데다.

1. `PayRepository` → Cloud Functions 호출로 교체 (`add()`를 지우고 서버가 쓰게)
2. `firestore.rules`의 `payEntries` 쓰기 차단
3. `PayConfig.debugTopUp` → 실제 조건으로 교체

나머지는 그대로 쓴다. `PayEntry` 원장 구조와 `balanceOf()` 합산 방식은 에스크로든 충전형이든 같다.

## 하지 말 것

- **잔액을 앱이 쓰게 두기.** 지금은 개발용이라 괜찮지만, 실제 돈이 오가면 조작 가능하다.
- **웹훅 없이 앱 콜백만 믿기.** 앱은 결제창을 닫고 꺼질 수 있다. 웹훅이 원본이다.
- **본인인증을 가입 단계에 넣기.** 이탈만 늘고, 출금하는 사람은 소수다.
- **PG 심사 전에 결제 UI부터 만들기.** 심사 결과에 따라 쓸 수 있는 결제수단이 달라진다.
